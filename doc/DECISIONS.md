# Decision records

Owner-resolved design decisions, recorded so implementation follows a written
decision rather than a conversation. Uses the vocabulary of
`doc/REQUIREMENTS.md`; background and the option analysis live in
`doc/HANDOFF-0.4.md` §5.

---

## D-1: Ids are host-minted (resolves HANDOFF-0.4 §5.1)

**Decided 2026-08-26.**

Node, edge, volume, mount, and lock ids are generated by the host, not by SQL.
The insert-view/trigger minting idiom (`node_new`, `edge_new`, and the
watermark-advancing triggers behind them) is retired in schema era 2. Guard
triggers that *defend* invariants (e.g. `node_guard_type`) remain; triggers no
longer *generate*. Direct INSERT with an explicit id remains the
import/recovery path, unchanged.

Why:

- Id generation is where silent divergence is catastrophic (the 2026-08-03
  zero-timestamp uuid7 bug was SQL-side generation failing quietly). Once
  Postgres and SQL Server backends exist, SQL-minting is one implementation
  *per backend dialect* — the scariest code in the system, three times, in a
  layer that fails silently. Host-minting is one implementation per host
  language, testable with ordinary unit tests and held identical across ports
  by conformance vectors.
- The `MAX(uuid7)` read-back in `db.create_monotonic` was the sole reason for
  the single-owning-connection model. Host-minting deletes the read-back, and
  the constraint goes with it — a prerequisite for several app servers
  sharing a Postgres backend, and for failover between a local file and a
  database copy.
- The expected trajectory is that concurrent/replicated deployments lean on
  the Rust engine, collapsing "one implementation per language" toward one
  implementation, period.

Obligations this creates:

- Each host implementation carries a vetted uuid7 mint with a monotonic
  counter in `rand_a` (see D-2 for the ordering contract).
- `conformance/` grows id-minting and fencing vectors that every port must
  pass before it ships.

## D-2: Per-mount watermarks fenced by a volume high-water mark (resolves HANDOFF-0.4 §5.2)

**Decided 2026-08-26.**

Neither pure stateless uuid7s nor the per-insert volume watermark. Instead:

- Each mount mints ids from its own **in-memory** monotonic watermark —
  strictly increasing within the mount, no shared state touched per create.
  The watermark is never persisted per mount; a restarted or crashed mount
  simply re-fences (below) from the volume row.
- The volume's existing `wm_ts`/`wm_seq` columns are reinterpreted as the
  volume's **high-water mark**. Coordination is loose and rare:
  - On attach, a mount initializes its watermark to
    `max(local clock, volume high-water mark)`.
  - Lazily (every T seconds or K ids) and on detach, a mount advances the
    volume row if its own watermark is ahead. Failure to write back is
    harmless; the next fence still bounds regression.

**Ordering contract** (this wording supersedes NODE-1's "stable time order"
and should be folded into REQUIREMENTS.md with the era-2 change):

1. Ids minted through one mount are strictly ordered.
2. Ids minted through different mounts separated by more than the
   coordination window are strictly ordered.
3. Within the window, cross-mount order is arbitrary — and correct: two
   unlocked concurrent writers have no defined "later" for the schema to
   report. A caller that needs a defined order takes the entry write lock
   (ACC-6/ACC-7, CV-3), which already serializes version advancement.

NODE-5 is mechanically unchanged: bytewise-greatest uuid7 always resolves one
winner. EXT-3's reserved child ordering is unaffected.

Why the fence (vs. pure stateless):

- **Clock regression across restarts.** A host clock stepping backward
  between sessions can never mint below what the volume has seen, so new ids
  cannot sort under existing ones and flip NODE-5 winners.
- **Failover with skew.** The high-water mark travels with the data. Failing
  over from a local file to a replicated copy onto a machine with a slow
  clock still fences above everything ever minted — ordering survives
  failover without trusting any clock. Physical replication (litestream)
  needs nothing extra; a future logical replication inherits the same
  guarantee.

## D-3: NODE-2 widens to fifo and socket; device nodes are refused

**Decided 2026-08-26.**

Schema era 2 widens the NODE-2 type vocabulary (a `node_guard_type` trigger
rewrite, by design) to add `fifo` and `socket`, and promotes symlink from the
NODE-6 metadata convention to a first-class type. Device nodes (block/char)
are refused: a device node on a data filesystem is a security surface with no
identified use case — CUDA/DMA devices live in `/dev` via devtmpfs/udev, and
container runtimes bind-mount `/dev` rather than storing nodes on a rootfs.
This stops short rather than closing the door: a future era adds `device` by
widening the same trigger, with no table migration.

## D-4: POSIX locks are per-mount; the compatibility table says so; mount policy guards the gap

**Decided 2026-08-26.**

fcntl byte-range locks and flock ship as kernel-arbitrated per mount (pinned
by `tests/test_posix_surface.py`). pyfuse3 exposes no lock handlers, so
cross-mount lock coherence is structurally out of reach for the Python
engine; schema-backed `getlk`/`setlk` (ACC-8 already forward-provisions the
columns) is the Rust engine's cross-mount upgrade.

> **Amended 2026-08-28**, when the era-2 branch absorbed the WebDAV work.
> The sentence above originally ended "...not a Python feature", and that
> clause is now wrong: the Python engine *does* have schema-backed
> cross-mount advisory locks — `lock`/`unlock`/`renew_lock` and the ACC-11
> exclusions, which WebDAV class 2 is built on, and which arbitrate between
> mounts exactly as this decision imagined.
>
> What survives is the narrower and still-true claim: the gap is the **FUSE
> path**, not the engine. pyfuse3 exposes no `getlk`/`setlk` handlers, so an
> `fcntl` call made by an application on a mount never reaches the daemon
> and cannot be routed to the engine locks that now exist. Wiring POSIX
> byte-range locks through to ACC-11 is the Rust engine's upgrade; the lock
> table it would drive is already there, and already used over HTTP.
>
> Everything below is unaffected — it reasons about fcntl/flock through a
> mount, which is still kernel-arbitrated per mount.

Two facts keep this safe rather than surprising:

- POSIX locks are advisory everywhere; they coordinate cooperating
  processes only, and processes on different mounts are not in the same
  cooperation domain (exactly as with NFS clients absent lockd).
- aloelite's own atomicity is cross-mount regardless: CV-3 version
  advancement under the schema-backed entry write lock serializes content
  commits between mounts. Overlapping writers cannot corrupt an entry; what
  they lose is only advisory signaling between their applications.

Accordingly, the 4.3 default mount policy is **one rw mount per subtree**;
overlapping rw mounts are an explicit admin opt-in. The compatibility table
states the per-mount lock scope plainly.

## Consequence for mount policy (HANDOFF-0.4 §4.3)

With D-1 + D-2, id correctness no longer depends on writer exclusivity.
"At most one rw mount per volume" is **not** a system invariant and must not
be treated as one; overlapping rw mounts (an admin mounting the volume root
while tenants mount subtrees, concurrently) are supported by the engine, with
entry write locks arbitrating write-write conflicts. Mount policy — access
mode (ro/rw), principal, per-subtree exclusivity where an admin wants it — is
authorization, configured per deployment, layered above correctness.
