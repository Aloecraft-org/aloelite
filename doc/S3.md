An S3-compatible endpoint, scoped to what a replication client actually calls,
so a backup tool can ship to an aloelite volume alongside the AWS bucket it
already uses.

---

## What it is, and what it is not

The surface was derived by reading [litestream][ls] 0.3.13's
`s3/replica_client.go` rather than the S3 API documentation. The docs describe
a hundred operations; that client calls eight:

| Operation | Request |
| --- | --- |
| ListObjects (**V1**) | `GET /<bucket>?prefix=&delimiter=&marker=&max-keys=` |
| GetObject | `GET /<bucket>/<key>` |
| PutObject | `PUT /<bucket>/<key>` |
| CreateMultipartUpload | `POST /<bucket>/<key>?uploads` |
| UploadPart | `PUT /<bucket>/<key>?partNumber=&uploadId=` |
| CompleteMultipartUpload | `POST /<bucket>/<key>?uploadId=` |
| AbortMultipartUpload | `DELETE /<bucket>/<key>?uploadId=` |
| DeleteObjects (batch) | `POST /<bucket>?delete` |

There is no `HeadBucket`, `CopyObject`, `CreateBucket`, versioning, ACLs,
tagging or lifecycle, because that client calls none of them. **A bucket is a
volume**, created through the manager's own API — the same posture the WebDAV
frontend takes.

Two details are not what an API summary would suggest, and both were worth the
reading:

- **Listing is V1.** Pagination is `Marker`/`NextMarker`, not a continuation
  token, and generations are enumerated through `CommonPrefixes` with
  `delimiter=/`. A V2-only implementation cannot enumerate a single
  generation.
- **Multipart is not optional.** Every write goes through
  `s3manager.Uploader`, whose default part size is 5 MiB. WAL segments land as
  a single `PutObject`, but any snapshot past 5 MiB becomes a real multipart
  upload with up to five concurrent `UploadPart` requests.

[ls]: https://litestream.io

## Enabling it

Off unless asked for, and — one step stricter than WebDAV — **enabled without
credentials is a startup error**, not an endpoint that authenticates nobody.

```bash
export ALOELITE_S3=1
export ALOELITE_S3_ACCESS_KEY=AKIAEXAMPLE
export ALOELITE_S3_SECRET_KEY=...            # or ALOELITE_S3_SECRET_FILE=/path
export ALOELITE_S3_BUCKETS=backups,archives  # optional; omit for every volume
aloelite-web
```

`ALOELITE_S3_SECRET_FILE` exists so the secret need not appear in the process
environment, where anything that can read `/proc` can see it.

**The S3 secret is not the volume PIN.** It is a separate credential with its
own scope, because a backup job holding the PIN could also unlock the volume
through every other frontend. A key can be scoped to a set of buckets, so one
endpoint serves several jobs without each holding the others' data.

Encrypted volumes must already be unlocked (through the API, the web UI, or
auto-mount) before the S3 frontend can serve them. There is nowhere to prompt
for a PIN inside an S3 request, so a locked encrypted volume is refused with
`AccessDenied` rather than half-served.

## Pointing litestream at it

```yaml
dbs:
  - path: /var/lib/discofetch/df.sqlite
    replicas:
      - url:      s3://backups/df
        endpoint: https://aloelite.internal:8080
        region:   us-east-1
        force-path-style: true      # REQUIRED -- see below
```

### `force-path-style: true` is required

**Litestream does not infer path-style addressing from `endpoint` alone.**
`s3.ParseHost` sets it only for hosts it recognises as a known provider
(Backblaze, DigitalOcean, Linode, Scaleway, Filebase, localhost); a bare
`s3://bucket/prefix` URL falls through to:

```go
} else {
    bucket = host
    forcePathStyle = false
}
```

Without the flag the SDK addresses buckets virtual-host style —
`https://backups.aloelite.internal:8080/key` — which needs wildcard DNS. Set
the flag, or set `ALOELITE_S3_VHOST_SUFFIX` on the manager and provide the DNS.

### Bucket names the manager owns

The frontend mounts at the application root so `endpoint` needs no path
component. Flask routes static rules ahead of dynamic ones, so the manager's
own paths still win — but a volume *named* one of them would be shadowed
rather than served, so those names are refused with `InvalidBucketName`:

`admin` · `dav` · `filesystems` · `health` · `s3` · `static` · `volumes`

## ETags are opaque, and why

An ETag here is `"<node-id>-<version>"`, not the object's MD5.

Aloelite's chunk addresses are taken over **ciphertext** (`db.py`:
`ch = chunk_hash(ct)`), so no plaintext digest exists anywhere in a volume.
Storing one beside the ciphertext would hand anyone with file access an
offline confirmation oracle — guess a document, hash it, compare — which is
precisely what a volume's `random` `enc_mode` gives up deduplication to avoid.

This costs less than it sounds. Real S3 also returns non-MD5 ETags for
SSE-KMS and for every multipart object, so clients must already tolerate them,
and multipart part ETags are round-tripped verbatim by the client. `content.version`
is a strong validator: it advances on every commit, so it identifies the
committed bytes exactly, which is all an ETag promises.

A tool that insists ETag == MD5 will not be happy. Litestream does not.

## Limits worth knowing before you rely on it

- **A key cannot be both an object and a prefix of other objects.** S3's
  keyspace is flat and permits `a/b` and `a/b/c` to coexist; a tree cannot.
  Refused with `InvalidRequest` rather than resolved arbitrarily. Litestream's
  layout is strictly hierarchical, so it does not hit this.
- **Multipart parts stage in memory** and are concatenated at Complete, so an
  upload is bounded by the staging cap and is *not* persisted across a manager
  restart. An interrupted upload is abandoned; the client retries the whole
  object, which it already handles.
- **Bodies are buffered to authenticate them.** SigV4 covers a payload hash,
  so the body must be in hand before the request can be trusted. The limit is
  64 MiB per request, comfortably above `s3manager`'s 5 MiB part size.
- **Chunked upload signing is refused by name.**
  `STREAMING-AWS4-HMAC-SHA256-PAYLOAD` is not implemented, and a request
  asking for it gets `NotImplemented` rather than having its chunk framing
  stored as content. `aws-sdk-go`'s `s3manager` buffers each part into a
  seekable slice, so it never asks.
- **One volume is one SQLite file with one writer.** Concurrent writes to
  *different* volumes are fully parallel (separate files, separate locks);
  writes to the same volume serialise, though the streaming writer commits per
  chunk rather than per upload, so they interleave rather than block for the
  length of a transfer.

## Planned: a write-only (drop-box) credential

**Requested 2026-08-31, not implemented.** A backup target wants a credential
that can *deposit* and cannot *read back*: a machine shipping backups should
be able to `PUT` objects and (optionally) `LIST` what it has written, but not
`GET` anything. That way a compromised backup client cannot exfiltrate the
history it has been feeding, and cannot read anyone else's.

The credential model already has the shape for it. `manager/sigv4.py`'s
`Credentials` carries a secret and an optional bucket scope; this adds a third
axis:

```python
Credentials(secret, buckets={"backups"}, permissions={"put", "list"})
```

with `permissions=None` meaning "everything", the current behaviour, and the
check landing next to the existing `may_access` call in `manager/s3.py`'s
`_session`. Roughly:

| Operation | Permission |
| --- | --- |
| `PutObject`, multipart upload | `put` |
| `ListObjects` | `list` |
| `GetObject` | `get` |
| `DeleteObjects`, `DeleteObject` | `delete` |

**Two things make this less simple than it looks, and both should be settled
before it is built:**

1. **Litestream needs `get` to restore and `delete` for retention.** A
   `{put, list}` token covers only the shipping half. Restore would need a
   second credential held somewhere else — which is arguably the point (the
   restore key is used once a year, under supervision) but it means the
   retention sweep also needs the privileged key, or retention stops working
   and the bucket grows forever. Splitting `delete` from `get` is the useful
   middle: `{put, list, delete}` lets litestream run unattended while still
   refusing to hand the data back.
2. **`delete` in a write-only token is most of the damage anyway.** Something
   that can delete every object does not need to read them to ruin the backup.
   The real protection is retention enforced by the *server* rather than the
   client — refuse a delete of an object younger than N days — which is a
   different and larger feature (S3 calls it object lock). Worth naming as the
   eventual destination so the permission set is not mistaken for it.

A `put`-only token with no `list` is also worth having: it is the strictest
useful form, and litestream cannot use it, but a simpler drop-box client can.

## Smoke-testing a live endpoint

`script/s3_smoke.py` exercises exactly the calls litestream 0.3.13 makes, in
the order it makes them, against a running manager:

```bash
python script/s3_smoke.py --endpoint http://127.0.0.1:7081 \
    --bucket backups --access-key AKIALOCALBACKUP --secret-key ...
```

A pass means put/get, implied prefixes on a deep key, flat listing, listing
with `delimiter=/` (CommonPrefixes), a multipart upload past the 5 MiB part
size, and a batch delete all work — which is the whole surface a replica
target needs. It cleans up after itself unless you pass `--keep`.

Requires `botocore` (`pip install botocore`), deliberately: the point of the
frontend is that an SDK talks to it, and a request signed by aloelite's own
code would only prove the verifier agrees with itself.

A quicker "is it even on" check, which needs nothing installed — an S3-enabled
manager answers an unsigned request with an `AccessDenied` XML body, while one
without the frontend 404s:

```bash
curl -s http://127.0.0.1:7081/backups
```

## Testing

`manager/test_s3.py` drives the frontend with a **real botocore client over a
real socket**, because the point of the frontend is that an SDK talks to it. A
request signed by aloelite's own code would only test the verifier against its
own canonicalisation. `manager/sigv4.py` is cross-checked the same way: the
tests sign with botocore and verify with our module, so any disagreement about
canonical form fails the suite.

The strongest end-to-end check is the one your deployment already has — point
litestream's own `test-backup.sh` at the endpoint and confirm
`litestream restore` produces a byte-identical database.
